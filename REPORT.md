# CLAIR Gateway — отчёт о реализации

**Задача:** прозрачный проксирующий микросервис между агентом и LLM API, автоматически сжимающий промпты через неизменяемый CLAIR Base. Код CLAIR Base не изменялся — взаимодействие только через `POST {CLAIR_BASE_URL}/compress`.

---

## 1. Стек и обоснование

| Компонент | Выбор | Почему |
|---|---|---|
| Рантайм | **Node.js 20+ / TypeScript (strict)** | Ожидаемая структура ТЗ (`main.ts`, `proxy.ts`, `compressor.ts`) фактически задаёт TS/Node. Strict-типизация фиксирует контракты (OpenAI-запрос, ответ CLAIR) на этапе компиляции. |
| HTTP-фреймворк | **Express** — единственная runtime-зависимость | Для прокси не нужно ничего тяжелее: маршрутизация, middleware, body-parser. Одна зависимость = минимальная поверхность атаки и маленький Docker-образ. |
| Тесты | **Vitest + supertest** | Интеграционные тесты гоняются на настоящем HTTP-стеке приложения с in-process моками CLAIR и LLM — быстрые (весь набор < 2 с) и детерминированные. |
| Логгер и .env | **Собственные, без зависимостей** | JSONL-лог специфичен для задачи (поля токенов/latency); 60 строк своего кода проще и безопаснее, чем pino + dotenv. |

## 2. Архитектура

```
Агент ── OpenAI format ──► Gateway: validate → decide → compress → forward → log ──► LLM API
                                   │                                    ▲
                                   ▼ (только HTTP)                      │ ответ — байт в байт
                              CLAIR Base (immutable) ───────────────────┘ (не участвует)
```

**Ключевые решения:**

1. **Адаптер к неизвестной схеме CLAIR.** Контракт `/compress` в ТЗ не зафиксирован, поэтому `compressor.ts` автоопределяет поля ответа (`compressed`, `compressed_text`, `data.…`, `result`) и токен-счётчики, а схема закрепляется переменными `CLAIR_TEXT_FIELD` / `CLAIR_RESPONSE_FIELD` — подстройка под реальный CLAIR **без изменения кода**. Поведение покрыто тестами на 4 разных формы ответа.
2. **Стратегия отказа конфигурируема** (`CLAIR_FAIL_STRATEGY`). Дефолт — `fail_open`: Gateway является оптимизацией, и агент не должен падать из-за неё; запрос уходит в LLM без сжатия с WARNING в логе. `fail_closed` (503 в формате OpenAI error) — для сценариев, где экономия обязательна.
3. **Защита от деградации.** Если сжатый текст не короче оригинала — уходит оригинал (`note: compression_no_gain`); экономия никогда не отрицательна.
4. **Байт-фидельность ответов.** Тело LLM пересылается как есть, без повторной сериализации; заголовки `content-encoding`/`content-length` не копируются, поскольку undici отдаёт уже распакованный поток — иначе клиенты получили бы битый gzip.
5. **Стриминг (`stream: true`).** SSE проксируется chunk-by-chunk без буферизации; таймаут LLM действует только до получения заголовков; обрыв соединения клиентом абортит upstream-запрос.
6. **Подсчёт токенов.** Приоритет источников: счётчики CLAIR → `usage` из ответа LLM (для `llm_response_tokens`) → эвристика (~4 символа/токен латиница, ~2 — кириллица). Источник фиксируется в тестах.

**Drop-in прозрачность:** агент меняет только `base_url`. Аутентификация гибкая: ключ из `LLM_API_KEY` либо проброс входящего `Authorization`. Остальные `/v1/*` маршруты (например, `/v1/models`) проксируются без сжатия.

## 3. Известные ограничения

- Точный контракт `/compress` предполагается (в ТЗ он не описан); при интеграции с реальным CLAIR достаточно выставить до 2 переменных окружения, код менять не нужно.
- Метрики Prometheus, кэш сжатия и rate limiting **осознанно не включены** (согласованный скоуп): точки расширения описаны в `docs/README.md` (раздел «Расширение»).
- Для стриминговых ответов `llm_response_tokens` не заполняется — в SSE-дельтах нет `usage`.
- Сжатие выполняется последовательными вызовами CLAIR на каждый текстовый блок; при большом числе сообщений возможен батчинг, если CLAIR его поддержит.

## 4. Как запускается и тестируется

```bash
npm ci && npm start          # сборка + запуск на :8080 (или: docker compose up --build)
npm test                     # 32 теста: все 7 сценариев ТЗ + unit-тесты компрессора
npm run mock:clair & npm run mock:llm &   # демо-моки без внешних сервисов и ключей
./examples/curl_test.sh      # smoke: health → сжатый запрос → bypass → 400
```

Покрытие сценариев ТЗ: 1 — базовый прокси (`proxy.test.ts`), 2 — сжатие вкл (включая точные числа 1000→650, ratio 1.54 из примера ТЗ), 3 — выкл по env, 4 — выкл по header (+ обратное включение header-ом), 5 — CLAIR недоступен (fail_open, fail_closed, таймаут), 6 — некорректный запрос (4 кейса 400), 7 — A/B (`ab.test.ts`), плюс JSONL-лог формата ТЗ, SSE, мультимодальные сообщения, passthrough, 404/429.
