# Архитектура CLAIR Gateway

## Схема

```text
┌──────────────┐        ┌──────────────────────────────────────────────┐        ┌──────────────┐
│    Агент     │        │                 CLAIR Gateway                │        │    LLM API   │
│ (без измен.) │ ─────► │  express: validate → decide → compress →     │ ─────► │  (OpenAI-    │
│              │  OpenAI│            forward → log                     │ OpenAI │  совмест.)   │
│              │ ◄───── │  ответ — байт в байт, SSE — chunk-by-chunk   │ ◄───── │              │
└──────────────┘        └───────────────────────┬──────────────────────┘        └──────────────┘
                                                │ POST /compress (только HTTP)
                                                ▼
                                        ┌─────────────────┐
                                        │   CLAIR Base    │
                                        │   (immutable)   │
                                        └─────────────────┘
```

## Жизненный цикл запроса `POST /v1/chat/completions`

1. **Валидация** (`validateChatRequest`): объект, `model`, непустой `messages`, `content` — строка или массив частей. Любое отклонение → `400` в формате OpenAI error.
2. **Решение о сжатии**: `X-Clair-Compress` (заголовок) → иначе `COMPRESSION_ENABLED` (env).
3. **Сжатие** (`compressMessages`): каждый текстовый блок каждого сообщения уходит в CLAIR (`POST /compress`, таймаут `CLAIR_TIMEOUT_MS`). Мультимодальные части (`image_url`, …) проходят без изменений. **Защита от деградации**: если сжатый текст не короче — отправляется оригинал.
4. **Обработка отказа CLAIR**: `fail_open` (по умолчанию) — идти в LLM с оригиналом и WARNING; `fail_closed` — `503` в формате OpenAI.
5. **Пересылка в LLM**: `buildUpstreamUrl` склеивает `LLM_PROVIDER_URL` и путь (не дублируя `/v1`); `Authorization` — из `LLM_API_KEY` либо проброс входящего.
6. **Ответ**: статус и тело — байт в байт; `content-encoding`/`content-length` не копируются (undici отдаёт распакованный поток). `stream: true` — SSE проксируется чанками, обрыв клиента абортирует upstream.
7. **Лог**: одна строка JSONL в `logs/gateway.jsonl` (см. [API.md](API.md)) — фиксируется на `finish`/`close` ответа, ровно одна запись на запрос.

## Структура проекта

```
clair-gateway/
├── src/
│   ├── main.ts        # сборка app (buildApp), запуск, graceful shutdown
│   ├── proxy.ts       # пайплайн проксирования: валидация, сжатие, пересылка, лог
│   ├── compressor.ts  # HTTP-клиент CLAIR Base + адаптер схемы ответа
│   ├── config.ts      # конфиг: env + .env, fail-fast на невалидных значениях
│   ├── logger.ts      # JSON-логи в stdout + JSONL-лог операций в файл
│   ├── errors.ts      # иерархия ошибок CLAIR + конструктор OpenAI error
│   └── tokens.ts      # эвристическая оценка токенов (латиница/кириллица)
├── tests/
│   ├── proxy.test.ts      # сценарии 1–6 ТЗ + SSE, мультимодальность, passthrough…
│   ├── compressor.test.ts # unit-тесты контракта CLAIR (9 форм ответа/отказа)
│   ├── ab.test.ts         # сценарий 7 (A/B) + формат JSONL-лога
│   └── helpers/           # in-process моки CLAIR/LLM, MemoryLogger, test-config
├── mocks/             # standalone демо-моки (node *.mjs, без зависимостей)

└── REPORT.md          # отчёт по заданию
```

## Принятые решения и почему

| Решение | Почему |
|---|---|
| **Адаптер схемы CLAIR** (автоопределение полей + env-оверрайды) | Контракт `/compress` в ТЗ не описан; адаптер снимает риск интеграции без изменения кода и покрыт тестами на 4 формы ответа |
| **Дефолт `fail_open`** | Gateway — оптимизация, а не критический путь: падение CLAIR не должно ломать агента; жёсткий режим доступен одной переменной |
| **Одна runtime-зависимость (Express)** | Меньше кода для аудита, крошечный образ; логгер/.env-парсер просты и специфичны для задачи |
| **Байт-фидельность ответа** (`res.send(raw)`, без ре-сериализации) | Прозрачность: агент получает ровно то, что вернул LLM, включая нестандартные поля |
| **Прокси прочих `/v1/*` без сжатия** | Настоящая drop-in замена: SDK вызывает `/v1/models` и прочее — всё должно работать |
| **Таймаут LLM только до заголовков** | Долгие стримы легитимны; обрыв клиента освобождает upstream |
| **`estimateTokens` с учётом кириллицы** | Точные счётчики доступны от CLAIR/LLM; эвристика нужна лишь как fallback — но должна быть честной для русских промптов |

## Тестирование

Тесты поднимают те же модули, что и прод (`buildApp`), и реальные HTTP-моки на `127.0.0.1` (ephemeral-порты) — проверяется весь сетевой путь: заголовки, авторизация, статусы, SSE.

- `tests/compressor.test.ts` — контракт с CLAIR: каноничный и альтернативные форматы, оценка токенов, кастомные поля, HTTP 500, невалидный JSON, пустой результат, таймаут.
- `tests/proxy.test.ts` — сценарии 1–6 из ТЗ, точные числа лога (1000→650, ratio 1.54), SSE, мультимодальный контент, no-gain, passthrough, 404/429, проброс `Authorization`.
- `tests/ab.test.ts` — сценарий 7 (A/B) и соответствие JSONL-лога формату из ТЗ.

## Расширение (осознанно не включено в скоуп)

- **Prometheus-метрики**: `logger.operation()` — единая точка, куда стекаются все события; достаточно подписаться там и экспортировать счётчики (`/metrics` добавляется одним роутом).
- **Кэш сжатия**: кэшировать следует пары «хэш текста + режим → результат» в `compressMessages`, до вызова `clair.compress`.
- **Rate limiting**: middleware до `createChatHandler` (in-memory token bucket по IP/сессии).
- **Батчинг сжатия**: если CLAIR научится принимать массив текстов, цикл в `compressMessages` сворачивается в один вызов.
